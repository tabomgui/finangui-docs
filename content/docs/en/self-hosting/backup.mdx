title: Backup
description: What to back up on a self-hosted instance, and how to dump and restore the database.
---

Two things need to survive, and only two: the Postgres data and `backend/.env`.

## The database

All of finangui's data — accounts, transactions, categories, everything — lives in the `db` service's Postgres volume (`db-data`, declared in `docker-compose.prod.yml`). Back this up on whatever schedule fits your risk tolerance; it's the only place application data is stored.

A straightforward way to dump it, using the `db` service and the database/user names from `backend/.env` (`finangui` by default for both):

```bash
docker compose -f docker-compose.prod.yml --env-file backend/.env exec db \
  pg_dump -U finangui finangui > finangui-$(date +%Y%m%d).sql
```

Restoring into a fresh, already-running `db` service:

```bash
cat finangui-20260101.sql | docker compose -f docker-compose.prod.yml --env-file backend/.env exec -T db \
  psql -U finangui finangui
```

## `backend/.env`, specifically `APP_KEY`

`backend/.env` also needs to be backed up — mainly for `APP_KEY`. Laravel uses this key to encrypt certain database columns, including the Pluggy `client_id`/`client_secret` that each user registers under [Configurações](/docs/features/banking) (Settings).

<Callout type="warn">
  If `APP_KEY` is lost, every value it encrypted becomes permanently unreadable — not just hard to recover, but mathematically impossible without the original key. Restoring a database dump with a different (or missing) `APP_KEY` than the one that encrypted it brings back rows your instance can no longer decrypt, such as stored Pluggy credentials; those bank connections would need to be re-registered from scratch. Keep `APP_KEY` backed up together with (but separately from) the database dump.
</Callout>
