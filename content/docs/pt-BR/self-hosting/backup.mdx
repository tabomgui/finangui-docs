---
title: Backup
description: O que fazer backup numa instância self-hosted, e como salvar e restaurar o banco de dados.
---

Duas coisas precisam sobreviver, e só duas: os dados do Postgres e o `backend/.env`.

## O banco de dados

Todo o dado do finangui — contas, transações, categorias, tudo — mora no volume do Postgres do serviço `db` (`db-data`, declarado no `docker-compose.prod.yml`). Faça backup disso na frequência que fizer sentido para o seu apetite a risco; é o único lugar onde o dado da aplicação é guardado.

Uma forma direta de gerar o dump, usando o serviço `db` e os nomes de banco/usuário de `backend/.env` (`finangui` por padrão para os dois):

```bash
docker compose -f docker-compose.prod.yml --env-file backend/.env exec db \
  pg_dump -U finangui finangui > finangui-$(date +%Y%m%d).sql
```

Restaurando num serviço `db` já no ar, novo:

```bash
cat finangui-20260101.sql | docker compose -f docker-compose.prod.yml --env-file backend/.env exec -T db \
  psql -U finangui finangui
```

## `backend/.env`, em especial o `APP_KEY`

O `backend/.env` também precisa entrar no backup — principalmente pelo `APP_KEY`. O Laravel usa essa chave para criptografar algumas colunas do banco, incluindo o `client_id`/`client_secret` da Pluggy que cada usuário cadastra em [Configurações](/docs/features/banking).

<Callout type="warn">
  Se o `APP_KEY` se perder, todo valor criptografado com ele fica permanentemente ilegível — não só difícil de recuperar, mas matematicamente impossível sem a chave original. Restaurar um dump do banco com um `APP_KEY` diferente (ou ausente) daquele que criptografou os dados traz de volta linhas que a instância não consegue mais decifrar, como as credenciais da Pluggy já cadastradas; essas conexões bancárias precisariam ser recadastradas do zero. Guarde o `APP_KEY` junto com o dump do banco (mas num backup separado dele).
</Callout>
